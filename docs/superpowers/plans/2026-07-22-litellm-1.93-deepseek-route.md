# LiteLLM 1.93.0 And DeepSeek Route Implementation Plan

> **For agentic workers:** Execute each task in order and keep runtime credentials under ignored `.spike-data`; never stage generated evidence or secret files.

**Goal:** Upgrade the Worker image to LiteLLM `1.93.0`, prove the existing Codex two-Turn acceptance against DeepSeek, and retain Kimi as a second explicitly selectable model profile.

**Architecture:** The Spike keeps one fixed LiteLLM upstream per Worker Runtime. The Backend resolves one server-owned model profile before a WorkerRun starts and injects only that profile's model, API base, and secret; the AgentTurn never switches providers automatically. The existing generic environment contract remains the M1 implementation surface, while the two verified profile values are documented as deployment choices.

**Tech Stack:** Docker, LiteLLM `1.93.0`, Codex `0.144.1`, `codex-acp` `1.1.2`, DeepSeek OpenAI-compatible Chat Completions, Kimi Anthropic-compatible Messages, Go E2E harness.

## Global Constraints

- `litellm[proxy]` stays exact-pinned at `1.93.0`; do not use `latest` or a version range.
- A WorkerRun selects exactly one model profile and receives exactly one upstream key.
- Do not implement request-level or mid-Turn automatic fallback.
- DeepSeek acceptance uses the same two-Turn fixture, Trace, Langfuse, token-absence, isolation, and cleanup checks as Kimi.
- Generated `.spike-data`, model credentials, logs, and acceptance evidence remain ignored and uncommitted.
- DeepSeek uses `deepseek/deepseek-v4-pro` with `https://api.deepseek.com`; the old `anthropic/...` route is only a diagnostic comparison.

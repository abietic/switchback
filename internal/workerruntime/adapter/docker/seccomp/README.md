# Worker seccomp baseline

`moby-default-v0.2.4.json` is the complete unmodified Moby profiles seccomp/v0.2.4 default profile, embedded by `worker_seccomp.go`. `LICENSE` is the upstream Apache-2.0 license copied without modification.

- Moby commit: `a5b58c94d334674eae3a3207d4f05417643a90d0`; [pinned dependency](https://github.com/moby/moby/blob/a5b58c94d334674eae3a3207d4f05417643a90d0/go.mod).
- Profiles commit: `245180c51918481c0525424b3ee025d2b435d46c`; [original profile](https://github.com/moby/profiles/blob/245180c51918481c0525424b3ee025d2b435d46c/seccomp/default.json), [original license](https://github.com/moby/profiles/blob/245180c51918481c0525424b3ee025d2b435d46c/LICENSE).

- Original license SHA256: `cfc7749b96f63bd31c3c42b5c471bf756814053e847c10f3eb003417bc523d30`.

The private builder checks the original bytes before transforming them. It removes only ioctl from the sole unconditional ALLOW group and appends disjoint masked low32 ioctl ALLOW prefixes covering all commands except FS_IOC_FSSETXATTR `0x401c5820`, FS_IOC_SETFLAGS long64 `0x40086602` and compat32/x32/ARM `0x40046602`. These commands, including arbitrary upper32 aliases, reach the original ERRNO/1 default. Blocking the setters also blocks their other file flag/hint changes; this is intentional. Original architecture maps, conditional rules, errno values and extension fields are retained; the Backend does not pre-resolve them.

The immutable server-owned JSON is attached to Worker ContainerCreate, covering the container process policy including shim, ACP, tools, SessionProcess and later exec. It is compared exactly at historical and both new-container inspect boundaries. Backend, observer and secret populator retain their existing policies. No Task/Agent policy input or unfiltered retry exists.

Engine Info must declare seccomp support and a reviewed architecture (`amd64`, `x86_64`, `arm64`, `aarch64`) before provisioning side effects. This only establishes a prerequisite. Source/fake tests and cross-compilation do not prove actual per-ABI profile loading, installed BPF, exec inheritance or rejection before XFS callees. If the Engine/runtime cannot load this full pinned baseline, provisioning/start must fail closed before Worker execution, without fallback. The exact profile-loading phase is runtime-dependent; the synthetic Create-rejection test only proves that such an error is propagated without an unfiltered retry. The pinned profile is not a claim of equivalence to every Engine version's builtin profile. Native acceptance and storage/capacity/execution authorization remain separate; this filter does not enable execution.

Production control reconnect also checks physical policy before the original durable journal Claim, Hub attachment, accepted ResumeAck or pending-command replay, including when gRPC serves before startup restore and no process-local credential has been registered. Startup restoration uses the same admission before opening/registering live credentials or adopting a runtime. Both checks call the same Provisioner's private immutable policy; no caller supplies expected policy bytes.

The read-only owner lookup binds Session/runtime/generation to the saved exact container ID or a consistent committed resident pin. Normal first Claim occurs before runtime.ready and activation reconciliation, while both durable CIDs are empty. Only for an exact starting owner with one matching live reserved resident association may the same Provisioner's process-local verified Create handoff supply the exact CID. The handoff is published after the second verifyCreated and pre-Start authority/context checks, immediately before ContainerStart; it is never inferred from a name, labels, claimant or Task field. A missing/conflicting owner, association or handoff fails closed.

The handoff has an independent mutex so a synchronous control Claim during ContainerStart does not wait on the Provisioner's lifecycle lock. Read-only lookup returns a value copy and does not consume it; an independent journal denial may be retried. Failed/unknown Start retains it. Only trusted cleanup confirming removal clears a matching exact CID/generation handoff. A fresh Backend/Provisioner has no handoff: without durable CID evidence it holds the original owner/quota and refuses adoption rather than guessing or rebuilding.

Handoff and durable pin are identity evidence only. Successful policy inspection still delegates to the unchanged journal's credential/channel/capacity authorization; admission never writes a resident pin. Inspection checks exact CID, container name and managed/owner labels, non-privileged HostConfig, exact SecurityOpt and Engine Linux/architecture/seccomp prerequisites. It does not prove that BPF is physically loaded.

Policy denial performs no durable Claim, credential restore, replay, cleanup, restart, recovery-incident creation, quota release or owner rewrite. General Inspect and trusted Cleanup remain independent of admission so a mismatched legacy owner can still be observed and reconciled. There is no automatic migration of existing containers.
